# Multi-worker consistency review — 17 September 2026

The application has useful shared-state protections, but it is **not yet safe to certify all concurrent writes or worker restarts**. This review fixes six concrete areas and records the remaining issues below. Multiple workers can expose these races more often; several also occur with concurrent requests in one worker.

This is a source review plus offline regression testing. No production records, running services, Oracle schema, or deployed containers were changed. SQLite tests verify stale ORM-state behavior and transaction outcomes, but SQLite does not implement Oracle `FOR UPDATE` scheduling. Actual Oracle contention, deadlocks, connection capacity, and shared-storage semantics still need deployment-level tests.

## Changes made

| Area | Problem | Change |
| --- | --- | --- |
| Execution attempts | Concurrent saves could pass the same `run_version` check and allocate the same attempt number. | Lock and refresh the execution before validating and saving. Bulk results lock selected executions in ID order. Single assignment, version upgrade, and attempt-defect changes use the same row lock. Attempt allocation uses the highest retained attempt number rather than row count. |
| Gateway draft lifecycle | Edit, cancel, and submit could each act on a previously loaded Draft; submission can create child workflows while another request cancels or edits the gateway. | Direct edit/cancel/submit routes now lock and refresh the gateway before checking its status. This does not cover the separate application-approval finalization path listed below. |
| Oracle lock SQL | Functional, SAST/DAST, Performance, Suppression and one cycle-link lookup combined `FOR UPDATE` with `.first()`, which adds a row limit incompatible with Oracle locking queries. | Use unrestricted `one_or_none()` for primary-key lookups. Existing missing-record behavior remains 404. |
| Workflow evidence uploads | Two workers could both see an unused filename; one then failed at exclusive creation. | Atomically reserve a filename with exclusive creation and retry collisions with a full UUID. Existing content is preserved. |
| Shared application logs | Separate workers used ordinary `RotatingFileHandler` on the same file; their rotation operations were not coordinated. | Use a POSIX file lock across reopening the active file, rotation, and writing. Reopening prevents workers writing into a file another worker already rotated. |
| Compose Document Portal storage | The main API performs workspace folder/quota operations, but its Document Portal root was not the document service's mounted repository. | Both services now mount the same host directory at `/data/qualityops/document-storage`, use its `repository` directory, and share SELinux labeling with `:z`. |

Code: `backend/app/routers/test_execution.py`, `backend/app/routers/qa_requests.py`, workflow router lookup helpers, `backend/app/documents.py`, `backend/app/process_logging.py`, `backend/app/logging_config.py`, and `docker-compose.yml`.

Row locking serializes overlapping database transactions. It does **not** prevent an old browser form from overwriting a newer completed edit unless that endpoint also checks a client-supplied revision. The existing `expected_run_version` check gains correct locking here; rich and bulk result routes still do not require a browser revision.

## Remaining findings

P1 means resolve before relying on the affected concurrent operation. P2 means a consistency, reliability, or capacity limitation requiring remediation or an explicit deployment decision. These are source-supported scenarios, not claims that each was reproduced on live Oracle.

| Priority | Finding and concrete trigger | Evidence | Recommended correction |
| --- | --- | --- | --- |
| P1 | **Project uniqueness is only checked before writing.** Two requests can both find no matching project and create duplicate normalized names or two non-archived projects for one application. | `routers/test_projects.py`: `_require_unique_project_name`, `_require_no_active_project_for_application`; corresponding `TestProject` model has no matching uniqueness constraint. | Check existing duplicate data, then add Oracle unique indexes for normalized names and the conditional non-archived application key. Map constraint failures to 409. |
| P1 | **Admin edits can replace newer values.** Two administrators load the same roles, department assignments or workspace membership list; the later save is not checked against the version originally read. | `routers/auth.py:update_user`, `update_local_admin_user`; `routers/qa_workspaces.py:replace_members`; project metadata editing. | Add revision fields and conditional updates/409 responses. Lock parent rows when replacing association collections. A lock alone does not detect an old form submitted after another commit. |
| P1 | **Document Portal rename/move/delete do not share the upload lock.** A target can appear after `exists()` and before rename/move, allowing an overwrite or unexpected move. A folder can also be deleted while an upload is writing inside it. First-use workspace-root creation has a separate mkdir/owner-marker race. | `routers/document_portal.py:rename`, `move`, `delete_item`, `delete_selection` versus `_store_file`; `document_portal_storage.py:workspace_root`. | Apply one consistent family/storage locking protocol to every mutation, revalidate paths inside it, and use atomic no-replace publication where available. Include workspace-root initialization and renames. The shared Compose mount fixed above is a prerequisite. |
| P1 | **Cycle state and execution writes are not one locked aggregate.** A result can validate an In Progress cycle while another transaction completes or blocks it. Bulk assignment/removal and cycle deletion do not all follow the new execution-row locking protocol. | `routers/test_execution.py:update_cycle`, `_prepare_execution_update`, `bulk_assign_executions`, `remove_execution`, `delete_cycle`. | Establish a documented lock order across Functional request, cycle and execution rows, then use it for every related mutation. Revalidate status after locking. Avoid adding inconsistent lock order piecemeal. |
| P1 | **Deferred application approval can finalize the same gateway concurrently.** Two approval/seed operations may both select the same Submitted gateways and generate child workflows. | `routers/applications.py:_approve_pending_application_name`; `routers/qa_requests.py:_finalize_child_requests`. | Lock application and gateway rows in consistent order, refresh/recheck terminal states, and make child creation idempotent with database constraints. Direct gateway submit locking does not cover this entry point. |
| P2 | **Some deletes commit in the middle of their parent operation.** `remove_execution` calls `delete_document`, which commits each document removal before the execution itself is deleted. A later failure leaves a partial operation and releases any transaction locks. | `routers/test_execution.py:remove_execution`; `documents.py:delete_document`. | Separate staging document deletion from transaction commit; commit parent and metadata changes once, then use the existing deletion journal for physical cleanup. |
| P2 | **Redis invalidation can be undone by an old reader.** Worker A reads old DB data, worker B commits and deletes cached data, then A puts its old result back into Redis. A lost invalidation during Redis failure has a similar stale-read window. | `cache.py:get_json`, `set_json`, `delete_prefix`; reference-data routers and dashboard summary. | Version cache entries/invalidation generations and conditionally publish results, or disable affected caches until the protocol is implemented. Current TTLs are 60 seconds for summary and 300 seconds for reference data. This affects reads, not DB persistence. |
| P2 | **Background job execution is process-local.** Status is shared, but queued Python callables are not durable. A worker exit loses queued/running work; another worker marks it failed when polled rather than resuming it. A DB commit may have succeeded before completion status was written. | `routers/jobs.py:_job_queue`, `enqueue`, `_run`, `_authorized_job`. | Use a durable queue with idempotent job identifiers/checkpoints if restart recovery is required. Do not blindly retry imports with uncertain commit outcomes. |
| P2 | **Request audit writes are best effort after the response.** A worker crash can lose the audit event after the business transaction committed. Some explicit audits also commit separately and suppress failures. | `main.py:_write_request_audit`, response `BackgroundTask`; `audit_service.py:write_audit`. | Persist required audit intent in the business transaction; deliver auxiliary audit records through a durable outbox. |
| P2 | **Shared login failures are not an atomic admission limit.** Several simultaneous attempts may all pass `enforce()` before any records a failure. | `login_rate_limit.py:enforce`, `record`, `clear`. | Use a shared atomic reservation/window algorithm if the limit must cap concurrent attempts as well as sequential failures. The current shared history is still better than worker-local counters. |
| P2 | **First-use business-counter creation can collide.** Existing counter rows serialize updates, but simultaneous MERGE inserts for an absent prefix can compete on the primary key. Counter row locks also remain held until the caller commits, limiting same-prefix throughput. | `models.py:_claim_business_seq`; initial schema creates `qap_id_counters` without populating every prefix. | Preseed supported prefixes in a controlled migration or use Oracle sequences. Test first-use and mixed-prefix transaction lock order. The primary key protects against duplicate counter rows; the likely first-use outcome is a failed request, not silent overwrite. |

## Existing protections verified in source

- Database sessions are created per request or background action and closed afterward; workers do not share a global ORM session. Engines/pools are process-local under the current Uvicorn worker command.
- Primary row IDs use database identities. Several important invariants have unique constraints, including used login challenges, execution attempts, cycle/testcase slots, and testcase version numbers.
- Login envelopes consume their challenge through a separately committed database uniqueness check. Replay handling is shared across workers rather than stored in Python memory.
- Most Functional, security and Performance workflow transitions already request row locks; this review corrects their Oracle lookup form. Testcase checkout/version changes already lock parent identities and refresh stale state.
- Notification outbox rows are durable and atomically claimed before delivery. SMTP delivery is **not exactly once**: a crash after SMTP accepts a message but before SENT is committed can cause a retry/duplicate. SLA notification evaluation locks its target row.
- Background-job status is atomically replaced on shared storage; live worker leases use filesystem locks. Orphan detection avoids silently replaying possibly committed imports.
- Workflow upload cleanup preserves files if a database commit outcome is uncertain; the deletion journal defers physical cleanup until the row deletion is confirmed.
- Workspace-aware frontend GET keys include token and selected workspace. Single-use encryption challenges are excluded from caching. Other tabs/users can still display their short-lived cached reads until refreshed.

## Deployment and capacity conditions

1. Rebuild/restart every API worker together to activate these code changes. Recreate both Compose services to apply the shared storage mount. Existing deployed data may be split across old paths; reconcile it before assuming the new mount contains every folder. No data was moved by this review.
2. All workers/replicas must use the same Oracle schema, JWT signing secret, login private key and persistent storage for the relevant module. Different keys can cause intermittent authentication/decryption failures depending on which worker receives a request.
3. POSIX `flock` must work across the actual mounted filesystem and all participating hosts. Tests here used local storage, not production NFS/SMB. Every writer of `app.log` must use the new handler; do not unlink its lock file while workers run.
4. Pool limits multiply per process. With code defaults, four API workers can use `4 × ((8 + 4) + (3 + 5)) = 80` Oracle connections across main and audit pools. Compose's two document workers add up to six main-pool connections; their initialized audit engines could add another sixteen if used. Replicas, migrations, administrators and other database clients need additional capacity. Pool limits are ceilings, not connections all opened at startup.
5. `BACKGROUND_JOB_WORKERS=2` is per API worker: four API workers permit eight job threads, competing with requests for their respective main pools. Measure before increasing worker count. A larger worker count does not remove database hot-row contention.
6. Redis keys use the fixed `qa_portal:` prefix. Isolate UAT and production by Redis database/instance (or implement environment-specific namespaces). A shared Redis database across deployments can mix cached reference data. Caching currently degrades to direct DB reads if unconfigured/unavailable.
7. Reports/dashboard pages make multiple SELECTs. Under Oracle READ COMMITTED, each SELECT has its own consistent view, so totals and detail queries can disagree during writes. Use an explicit reporting snapshot where a reconciled point-in-time report is required.

## Validation

`backend/tests/test_multiworker_safety.py` adds coverage for:

- Four separate processes writing and rotating one log: all 320 records retained exactly once within the test retention budget.
- Four separate processes uploading the same filename: all 48 distinct contents preserved.
- Stale execution session rejected with 409 after another session records a result.
- Attempt numbering after a gap in retained attempt history.
- Bulk execution locks selected rows in ID order.
- A stale gateway submission rejected after another session cancels it.
- Oracle-dialect compilation of representative locked lookups without FETCH FIRST/ROWNUM.

The Compose file was parsed and checked for matching repository paths, mount sources, targets and shared SELinux labels. Full backend suite: **561 tests and 79 subtests passed** (`python3 -m pytest tests -q --disable-warnings --tb=short`), including all 11 new multi-worker regression tests. The suite reported 316 warnings, primarily dependency/deprecation warnings; these were not treated as failures.

Still required before a multi-worker release sign-off: parallel API calls against a disposable Oracle schema, actual worker termination during imports/audit/SMTP, concurrent cycle-state/result operations, concurrent project creation, file rename/upload/delete races, shared-volume lock tests on the deployment filesystem, and load testing with the configured Oracle connection budget. These tests must verify business outcomes and file contents, not only HTTP success rates.
