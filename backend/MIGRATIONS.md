# Oracle schema migrations with Alembic

Alembic tracks QualityOps schema changes in `qap_alembic_version`.
The connection URL always comes from the same `DATABASE_URL` used by the API;
credentials are never stored in `alembic.ini`.

## One-time adoption for an existing database

1. Back up the Oracle schema.
2. Install the backend requirements.
3. Confirm the application starts successfully against the current schema.
4. Check for model/schema differences without applying DDL:

   ```bash
   cd backend
   alembic check
   ```

   The initial revision represents the production schema captured when
   Alembic was adopted. An older database may report differences caused by
   historical manual SQL. Investigate them before stamping; never accept
   autogenerated destructive operations without review.

5. Mark the verified existing schema at the baseline:

   ```bash
   alembic stamp 1745115668f0
   alembic current
   ```

`stamp` only creates/updates `qap_alembic_version`; it does not alter business
tables or data.

## New empty database

For a completely empty Oracle user, apply the full migration chain and then
run the seed. Do not stamp an empty schema: stamping records a revision without
creating its tables.

```bash
cd backend
alembic upgrade head
python -m app.seed
```

On a fresh installation, migrations do not create an organisation workspace.
The seed creates the sole automatic workspace, key `DEFAULT` and name
`Default Workspace`, then adds every System Administrator as a required
member. Organisation workspaces are created later by an Administrator.

Deployments must run `alembic upgrade head` before starting the API.

## Department unit hierarchy

Revision `d4f8a2c6e901` adds optional hierarchical units beneath each canonical
department. It also adds unit scope to users, QA requests, Test Projects,
Workspace routing rules, and Department Coordinator assignments. Existing
records remain department-wide because every new foreign key is nullable.

Apply it with the normal deployment command:

```bash
cd backend
alembic upgrade head
```

After deployment, create units under **Administration → Departments**, assign
them to users, and add unit-specific Workspace coverage only where routing
must differ from the department-wide fallback.

## Creating a schema change

1. Update the SQLAlchemy models.
2. Generate a candidate revision:

   ```bash
   cd backend
   alembic revision --autogenerate -m "add concise change description"
   ```

3. Review both `upgrade()` and `downgrade()`. In particular, check Oracle
   identifier lengths, `VARCHAR2` sizes, identity columns, indexes, constraint
   names, nullability changes, and any data backfill required before making a
   column non-nullable.
4. Test both directions on a disposable Oracle schema:

   ```bash
   alembic upgrade head
   alembic downgrade -1
   alembic upgrade head
   alembic check
   ```

5. Commit the model and revision together.

## Normalized assignment history

Revision `a31e7d92c4f0` creates `qap_assignment_history`, which stores one
effective-dated tenure per assignee, entity, and assignment role. Apply it with
the normal deployment command:

```bash
cd backend
alembic upgrade head
```

Existing current assignments are adopted lazily when their next assignment
change occurs. This avoids inventing historical start times or actors that the
legacy data cannot prove. New and changed assignments are recorded immediately,
and management users can query the normalized history through
`GET /api/approvals/assignment-history`.

## Deployment commands

### Docker Compose

The production Compose stack includes a one-shot `migrate` service. It runs
from the same backend image and must complete successfully before the backend
health check and frontend startup are allowed to proceed:

```bash
docker compose build backend migrate
docker compose run --rm migrate
docker compose run --rm migrate alembic current
docker compose up -d
```

`DATABASE_URL` and `SECRET_KEY` are required Compose variables. The backend
image contains `alembic.ini`, the Alembic environment, and the complete
revision history; local `.env`, virtualenv, logs, uploads, and Python cache
files are excluded by `backend/.dockerignore`.

### Direct backend environment

```bash
cd backend
alembic current
alembic upgrade head
alembic current
```

For SQL review without applying it:

```bash
alembic upgrade head --sql > migration.sql
```

Do not run `alembic stamp` as a normal deployment command. Stamping is only
for the one-time baseline adoption or a specifically approved recovery.

## Workspace defect workflows

Revision `a8d3e5f70912` adds versioned workspace policy storage, per-defect
workflow snapshots/history and revision tracking, and widens defect status to
40 characters. Existing defects retain their legacy workflow. Apply before
starting the updated API. See `../docs/defect-workflows.md` for configuration,
closure rules and verification. Automatic downgrade is intentionally refused
because it would discard workflow history or truncate modern statuses.


## Optional defect QA request link

Revision `b9e4f6012a38` makes `qap_defects.qa_request_id` nullable and adds
`qa_workspace_id` and `department`, backfilled from existing requests. New
standalone defects retain explicit workspace/department ownership; request
links remain optional and may be added later with scope checks. Apply before
starting the updated API. Existing request links and workflow versions remain.
